# Contributing

Thanks for helping. This project is small and early, so a short issue before a big change saves everyone time.

## What lives where

| Folder | What it is |
|---|---|
| `template/` | The hub a team receives: the board, the `./hub` tool, setup, starter knowledge pages, agent rules. A standalone project with its own `package.json` and lockfile. |
| `packages/create-hackathon-hub/` | The scaffolder behind `pnpm create hackathon-hub` |
| `docs/` | How it works and the playbook, for people deciding whether to use it |

## Run the checks

You need Node 22.12 or later and pnpm for development. The hub a team receives still runs on Node 20.9, but the test runners here do not. CI runs on Node 22.

The hub, from inside `template/`:

```bash
cd template
pnpm install
pnpm typecheck
pnpm test:all
pnpm build
```

The scaffolder, from the repo root:

```bash
node --test "packages/create-hackathon-hub/test/*.test.mjs"
```

To see a board full of sample data, from `template/`:

```bash
HUB_LOCAL_DIR=tests/fixtures/demo-hub pnpm dev
```

To try the whole path by hand, scaffold into a scratch folder and run setup with every outside step turned off:

```bash
node packages/create-hackathon-hub/index.mjs /tmp/scratch-hub --no-setup --no-git
cd /tmp/scratch-hub
./hub setup --dry-run
./hub setup --skip-github --skip-vercel --skip-tokens
```

Never run setup or the scaffolder without `--dry-run` or those three skip flags while `gh` and `vercel` are logged in. A plain run creates a real GitHub repo and a real deploy.

## The two rules that matter

1. **The tool stays dependency free.** `./hub` (everything under `template/scripts/`) and `template/lib/hub/*.mjs` import Node built-ins only. Teammates run `./hub` right after `git clone`, before anyone has run an install. The board can use packages; the tool cannot.
2. **Nothing event-specific outside `hub.config.json` and `team.json`.** An event name, date, time zone, base path, repo, or person hard-coded anywhere else is a bug, because the next team gets it too. Read them through `template/lib/hub/config.mjs`.

A few more conventions:

- Validate outside input in the board with zod.
- Return `{ data, error }` from functions at module boundaries instead of throwing.
- No em dashes in code, comments, docs, or strings.
- Never commit real names, tokens, unlock links, or anything from a real team's hub. Examples use Ada, Grace, and Linus Example, and the "Sample Hackathon".
- `template/docs/agent-prompt.md` is generated by setup from `template/docs/agent-prompt.template.md`. Edit the template file.

## For maintainers: the scrub check

Every commit to this public repo is permanent, so a pre-push hook scans what you are about to push. Turn it on once per clone:

```bash
git config core.hooksPath .githooks
```

The hook runs `node scripts/scrub-check.mjs --pre-push`. It scans the tree of each pushed commit and the files every new commit changed, for personal email addresses, token and key shapes, real unlock links, absolute home folder paths, and private artifact links. It also requires every new commit's committer email to be a GitHub noreply address. `SCRUB_ALLOW_IDENTITY=1` skips that one check, for pushing a contributor's commits. Never push with `--no-verify`.

`node scripts/scrub-check.mjs --tracked` runs the same checks on every tracked file; CI runs it too. A line containing `scrub-check: allow` is skipped by the built-in checks; use it rarely.

A maintainer can also keep a private terms file, one term per line, at `.private/scrub-terms.txt` in the main checkout or wherever `SCRUB_TERMS` points. Any hit fails the check. The file is local and is never committed.

## Proposing a change

1. For anything bigger than a typo, open an issue first and say what problem it solves.
2. Fork, branch, and keep the pull request to one change.
3. Add a test for any logic that would be painful to debug.
4. For a visible change to the board, add screenshots at phone and desktop width.
5. Run the checks above and say in the pull request which ones you ran.

## Contributing with a coding agent

Agent-written pull requests are welcome. Give your agent this file as its instructions; everything it needs is here. Paste this to it as a start:

```text
Read CONTRIBUTING.md and follow it. The rules that matter:
- Work only in the folder the change belongs to: template/, packages/create-hackathon-hub/, or docs/.
- template/ is standalone. Never import from outside it, and never add it to a workspace.
- Code under template/scripts/ and template/lib/hub/ imports Node built-ins only.
- Nothing event-specific outside hub.config.json and team.json.
- Never run ./hub setup or the scaffolder without --dry-run, or without
  --skip-github --skip-vercel --skip-tokens. Never deploy or push.
- No em dashes. No real names; use Ada, Grace, and Linus Example.
- Before you say you are done, run the checks in CONTRIBUTING.md and show their output.
```

`template/AGENTS.md` holds the rules a team's agents follow inside a hub. Read it if your change touches how agents use the hub; it is not the rule set for working on this repo. The root `AGENTS.md` is: the maintainer's agents load it in every session here.

You are still the author, so:

- Read the whole diff before you open the pull request. You should be able to explain every line.
- Paste the real output of the checks, not the agent's summary of them.
- Keep the pull request as small as a person would write it. Agents happily rewrite a file to change one line.
- Say in the description that an agent helped and which one. It changes nothing about review; it helps reviewers know what to look for.
